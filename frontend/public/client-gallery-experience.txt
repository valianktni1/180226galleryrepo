# CLIENT GALLERY EXPERIENCE — Complete Technical & UX Breakdown
# What we built for the couples viewing their wedding photos & videos
# ===================================================================

## OVERVIEW
When a couple receives their gallery link (via email or QR code), they enter a
fully branded, cinematic experience for viewing, downloading, and interacting
with their wedding media. Every detail — from how images load, to how videos
stream, to the slideshow with music — has been carefully engineered for a
premium, professional feel.


## 1. ACCESS & AUTHENTICATION
---------------------------------------------------------------------------
- Couples receive a shareable link (e.g. weddingsbymark.uk/s/abc123)
- Links are password-protected — couple enters the password provided by admin
- Access levels are configurable per link: "view only", "download", or "full"
  (full = download + upload + favouriting)
- Links can have optional expiry dates (auto-expire after wedding season)
- Custom vanity slugs supported (e.g. /s/eva-and-ella instead of /s/abc123)
- Links can be toggled active/inactive by admin at any time
- Guest Upload links are a separate share type — opens a simplified upload-only
  interface for wedding guests to contribute their own photos

## 6. PROGRESSIVE IMAGE LOADING (Lightbox Only)
---------------------------------------------------------------------------
When a couple clicks a photo to open the full-screen lightbox:

### How It Works (ProgressiveImage Component)
1. Thumbnail (400px) loads instantly — displayed with 10px blur filter
2. Full preview (1600px) loads in background via `new Image()` preloading
3. When the full image loads, it crossfades in with 0.4s ease-out transition
4. Blur filter animates from `blur(10px)` to `none`

### Smart Preloading
- When navigating the lightbox, the next 3 images ahead are preloaded in the
  background so they're instant when the couple swipes forward
- Uses `new Image()` objects to warm the browser cache silently

### Result
- Instant response when clicking any photo (thumbnail appears immediately)
- Smooth blur-to-sharp transition feels premium, not jarring
- Forward navigation feels instant because images are pre-cached

## 10. VIDEO STREAMING & PLAYBACK
---------------------------------------------------------------------------

### Backend Processing Pipeline (What happens when admin uploads a video):

1. CHUNKED UPLOAD
   - Videos upload in 1MB chunks — supports files up to 40GB+
   - Progress tracked in real-time on admin interface

2. THUMBNAIL GENERATION (Instant — via thumbnail_executor, 8 workers)
   - FFmpeg extracts a frame at the 1-second mark
   - Creates 400x400 thumbnail and 1600x900 preview
   - Runs in separate ThreadPoolExecutor (8 workers) — never blocked by transcoding
   - Couple sees video thumbnail in gallery within seconds of upload

3. FASTSTART OPTIMISATION
   - `ensure_video_faststart` runs on the original file
   - Moves the moov atom (video metadata) to the start of the file
   - Allows instant playback without downloading the entire file first
   - Uses: `ffmpeg -c copy -movflags +faststart`

4. WEB-OPTIMISED TRANSCODING (Background — via transcode_executor, 2 workers)
   - Creates a `.web.mp4` version optimised for streaming:
     - Resolution: 1080p (scaled width preserving aspect ratio)
     - Bitrate: 5Mbps H.264
     - movflags: +faststart (instant web playback)
   - GPU-ACCELERATED (AMD Radeon 780M via VAAPI):
     - First attempts: `-hwaccel vaapi -c:v h264_vaapi`
     - Uses hardware encoder for dramatic speed improvement
     - If GPU fails: automatic CPU fallback with libx264
   - Separate ThreadPoolExecutor (2 workers) — long transcode jobs don't
     block thumbnail generation
   - Real-time progress: FFmpeg runs with `-progress pipe:1`, progress
     parsed live and stored for polling
   - Admin sees per-file progress bars updating every 2 seconds

### NGINX Direct Video Serving (What happens when couple plays a video):

1. Couple clicks a video → Frontend requests a signed URL from the backend
2. Backend generates a secure URL:
   - Secret key shared between backend and NGINX
   - MD5 hash: `md5(secret + uri + expires_timestamp)` → base64
   - URL: `/video/{gallery}/{subfolder}/{file}.web.mp4?md5=xxx&expires=xxx`
   - Expires after 2 hours
3. Frontend redirects to the NGINX video container
4. NGINX `secure_link` module verifies the MD5 signature and expiry
   - Invalid/expired = 403/410 error
   - Valid = serves file directly from disk
5. NGINX serves with:
   - `sendfile on` — kernel-level file transfer (zero-copy)
   - `tcp_nopush on` + `tcp_nodelay on` — optimised TCP
   - `Accept-Ranges bytes` — supports seeking (HTTP Range requests)
6. Result: Smooth, buffer-free playback with instant seeking

### Video Player (Frontend — video.js 8)
- Full-featured HTML5 player with custom controls
- Playback speed options: 0.5x, 1x, 1.25x, 1.5x, 2x
- Picture-in-Picture support

## 14. LIVE VISITOR TRACKING (Silent Background)
---------------------------------------------------------------------------
- Every 30 seconds, the gallery sends a "heartbeat" to the backend
- Contains: session_id, current action, current subfolder, device type
- Actions tracked: "browsing", "viewing Wedding Images",
  "viewing lightbox DSC_0234.jpg", "downloading Video"
- Admin dashboard shows real-time: which couples are viewing, what they're
  looking at, how long they've been active, what device they're using
- Sessions cleaned up after 60 seconds of inactivity
- Completely invisible to the couple — no UI impact


## 15. ACTIVITY TRACKING

- Gallery views (when they open the share link)

- Individual file downloads (with exact filename)

- Album submissions
- Admin can search, filter, archive, and clear logs
